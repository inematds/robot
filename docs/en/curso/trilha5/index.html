🧠 Modern AI and robotic arm

Language models, voice, and vision on the robot, with safety built in: the model chooses, the code checks, the microcontroller executes. Then, an SO-101 arm that learns tasks by watching you demonstrate them, also trained in simulation. Finally, an assistant robot that listens to a request, plans, and picks up an object.

How to read this map: The first three steps (teal) build the pieces: a safe brain with a local model, offline voice, and a working SO-101 arm. The next two (cyan) teach the arm: through demonstrations and in simulation. The final step, with a glow, brings everything together in the assistant. If you already know a step, skip to the next one.

🦾 What you’ll build in this track

An assistant that listens to “pick up the red cube,” understands the request with a local language model, checks the action against a fixed list, and uses an SO-101 arm you trained to pick up the object. Along the way, you’ll build a brain with Ollama that accepts only permitted actions, a Portuguese voice pipeline that works offline, a calibrated leader/follower pair, and a policy trained on your demonstrations.

  • ✓Local models: no cost per request
  • ✓Layered safeguards and a physical stop
  • ✓LeRobot with checked commands
  • ✓Simulation before the real arm

💡 Don’t have the arm yet?

Modules 5.1 and 5.2 run on a regular PC, with the ESP32 from Track 1 or in simulation mode. Module 5.5 trains the SO-101 digital twin in simulation. Buy the arm when you reach 5.3.

🧠 Language model as the brain

LLM, VLM, and VLA on the robot; the architecture where the model only chooses actions from a fixed list; Ollama running locally; and safeguards that protect the motor.

What it is:

Text to text, image with text to description, and image with instruction to movement: three model types, each in a different place in the robot stack.

Why learn this:

Avoid asking a text model to control a motor in real time.

Key concepts:

Parameters · inference · token · VLA.

What it is:

The model stays at the high level; a code validator checks the action before it becomes a command over serial.

Why learn this:

Models can make mistakes confidently; keeping these steps separate prevents mistakes from reaching the motor.

Key concepts:

High level · validator · hallucination · final safeguard.

What it is:

A menu of actions with parameters and limits, provided to the model as JSON Schema.

Why learn this:

Turn an open-ended response into a closed, testable problem.

Key concepts:

JSON Schema · enum · limits · tool use.

What it is:

Ollama on localhost and a complete Python script that asks, validates, and sends commands to the ESP32 (with simulation mode).

Why learn this:

Works without internet and has no per-request cost; cloud models also work with the same validator.

Key concepts:

/api/chat · format · temperature 0 · pyserial.

What it is:

Take a picture and ask the local vision model what’s in the scene.

Why learn this:

Gives context to the planner without handing it control of the motor.

Key concepts:

images in base64 · context · detector vs. VLM.

What it is:

Four layers: validator, limits repeated on the ESP32, command watchdog, and physical stop.

Why learn this:

Any model you plug in later operates within a box you control.

Key concepts:

Layers · watchdog · confirmation · power switch.

🎙️ Local voice: listen and speak

Offline voice pipeline in Portuguese: Whisper listens, the 5.1 brain decides, and Piper responds, with a wake trigger, spoken confirmation, and measured latency.

What it is:

Four separate stages: microphone, speech recognition, brain, and speech synthesis.

Why learn this:

Testing each stage on its own shows where errors and delays occur.

Key concepts:

STT · TTS · VAD · 16 kHz mono.

What it is:

Record from the microphone and transcribe in Portuguese with faster-whisper, on CPU or GPU.

Why learn this:

If recognition gets it wrong, everything else goes wrong too.

Key concepts:

Model size · int8 · language="pt" · VAD.

What it is:

Press to talk or say “hey, robot,” and where to place the microphone to avoid motor noise.

Why learn this:

A robot that obeys any phrase in the room is unpredictable.

Key concepts:

Trigger · openWakeWord · state machine · noise.

What it is:

The complete Python assistant: listen, choose, validate, confirm by voice, execute, and respond.

Why learn this:

Voice is just another input; the validator stays the same.

Key concepts:

Import modules · spoken confirmation · fail-safe.

What it is:

Lightweight speech synthesis with pt_BR voices that runs on Pi 5 without a GPU.

Why learn this:

A robot that tells you what it’s going to do gives you time to stop it if that’s not what you wanted.

Key concepts:

.onnx voice · phoneme · piper-tts · audio output.

What it is:

Measure the time for each stage and decide what can leave your home.

Why learn this:

You optimize the real bottleneck and avoid issues with students’ voices in the classroom.

Key concepts:

Bottleneck · offline · voice data · consent.

🦾 SO-101 arm and LeRobot

The leader/follower pair with Feetech STS3215 servos: IDs, calibration, LeRobot installation, first teleoperation, cameras, and the safety routine.

What it is:

An open-source, 3D-printed arm pair and the Hugging Face library that covers everything from motors to policies.

Why learn this:

It’s the shortest, cheapest path to an arm that can learn a task.

Key concepts:

Degree of freedom · leader/follower · STS3215 · policy.

What it is:

Find the ports, write each servo’s ID, assemble the arm, and measure the limits of each joint.

Why learn this:

Wrong IDs or poor calibration cause most cases of an arm shaking or moving in the wrong direction.

Key concepts:

Bus · find-port · setup-motors · calibrate.

What it is:

Virtual environment, feetech extra, USB port permissions, and a recorded version.

Why learn this:

AI robotics libraries change quickly; isolating the environment and pinning the version keeps the project running.

Key concepts:

venv · extras · dialout · --help.

What it is:

You move the leader and the follower copies it, in a loop running dozens of cycles per second.

Why learn this:

The 5.4 policy imitates exactly how you teleoperate.

Key concepts:

Control loop · target position · initial pose.

What it is:

Two fixed cameras, steady lighting, a simple background, and marked positions on the table.

Why learn this:

The camera is the policy’s main sensor; changes in the scene confuse the model.

Key concepts:

find-cameras · index_or_path · range · display_data.

What it is:

Clear area, power switch within reach, fixed base, and a routine before each session.

Why learn this:

A trained policy may make a movement you didn’t expect.

Key concepts:

Physical stop · torque · pinch point.

🎓 Learning by demonstration

Record episodes with the SO-101 pair, publish the dataset, train an ACT policy, evaluate it on the real arm, and explore policies that understand language.

What it is:

Instead of programming the movement, you demonstrate the task several times and a model learns to imitate you.

Why learn this:

Tasks like picking up varied objects are hard to program by hand and easy to demonstrate.

Key concepts:

Imitation · episode · observation · action.

What it is:

Teleoperate while LeRobot saves camera images and joint positions in episodes.

Why learn this:

The quality and variety of the demonstrations determine the training result.

Key concepts:

Episode · reset · variation · task description.

What it is:

Store, view, and share recorded episodes in the LeRobot format.

Why learn this:

Reviewing the data before training avoids wasting GPU time on poor demonstrations.

Key concepts:

Dataset · Hub · visualization · data version.

What it is:

Train the small, fast ACT policy on an NVIDIA GPU or in Colab.

Why learn this:

It’s the first training run that fits a maker’s budget and works with just a few dozen episodes.

Key concepts:

Policy · training steps · checkpoint · loss.

What it is:

Run the trained policy on the follower arm with lerobot-rollout, safely, and count how many times it succeeds.

Why learn this:

Measured success rate is the only honest way to say the arm has learned.

Key concepts:

Success rate · attempts · common failures.

What it is:

VLA models that receive a text instruction along with camera feeds: the small SmolVLA and the larger pi0 family.

Why learn this:

The same policy can perform different tasks depending on the request.

Key concepts:

VLA · fine-tuning · base model · GPU cost.

🧪 Simulate before going real

Why train in simulation, the SO-101 twin in MuJoCo, when Isaac is worth it, turning a photo of your table into a scene, and the gap between simulation and reality.

What it is:

Test and train in a virtual world, where collisions break nothing and time can run faster.

Why learn this:

It saves parts, human demonstrations, and scares at the workbench.

Key concepts:

Simulator · physics · scene · cost of errors.

What it is:

The lightweight, open simulator, with a model of the SO-101 that moves like the real arm.

Why learn this:

It runs on a regular laptop and lets you test before you have the arm.

Key concepts:

MuJoCo · digital twin · MJCF model · joints.

What it is:

NVIDIA’s simulation platform, with realistic graphics and many robots running in parallel, requires a powerful NVIDIA GPU.

Why learn this:

Knowing when the extra horsepower is worth it helps you avoid building a setup bigger than the problem requires.

Key concepts:

Isaac Sim · Isaac Lab · parallelism · GPU requirements.

What it is:

Build the simulated scene from photos of your workbench, with objects in their real positions.

Why learn this:

The more closely the simulation matches your table, the more useful the training will be on the real arm.

Key concepts:

Real2sim · reconstruction · scene · object.

What it is:

What changes when the policy moves from simulation to the arm: friction, play, lighting, camera.

Why learn this:

Understanding the gap helps you reduce it instead of blaming the model.

Key concepts:

Sim2real · domain randomization · real-world fine-tuning.

What it is:

Automatically create episodes in simulation and combine them with real demonstrations.

Why learn this:

This reduces the number of human demonstrations you need to record.

Key concepts:

Synthetic data · real + simulated mix · comparison.

🦾 Final project: assistant robot

From defining the scope and rules to turning voice into a plan, using vision and an arm to pick up objects, integrating a mobile base, measuring success, and presenting the project.

What it is:

Define what the assistant does, what it refuses, and the safety rules before writing code.

Why learn this:

A small, well-defined scope is what makes a final project work on presentation day.

Key concepts:

Scope · requirements · action list · completion criteria.

What it is:

The spoken request becomes a short sequence of actions from a fixed list, checked step by step.

Why learn this:

Real requests have multiple steps; the entire plan needs validation and must run with pauses.

Key concepts:

Plan · sequence · validation · confirmation.

What it is:

The camera finds the requested object, and the policy trained in 5.4 makes the arm pick it up.

Why learn this:

This is where perception and action need to agree in the real world.

Key concepts:

Detection · policy · pick and place · verification.

What it is:

Combine the mobile robot from earlier learning paths with the arm, accounting for power, weight, and communication.

Why learn this:

Integrating systems that work on their own is where real problems show up.

Key concepts:

Integration · center of mass · separate power · states.

What it is:

A repeated test plan, success rate for each step, and a record of failures.

Why learn this:

The numbers show what to improve and keep you from relying on a video that only worked once.

Key concepts:

Success rate · time per task · failure log.

What it is:

Publish the README, a real-time video, the dataset, and the code so others can reproduce the project.

Why learn this:

A documented project becomes a portfolio piece and helps the next person get started.

Key concepts:

README · honest demonstration · license · community.

🧰 Trail kit

What the learning path uses beyond the robot from earlier paths. Approximate range of R$ 1.800 a R$ 4.500 not including the computer (Oct/2026; check before buying: the arm is usually imported, and the price varies widely with assembly, shipping, and exchange rates).

🦾 Arm

SO-101 leader-follower pair: 12 Feetech STS3215 servos, two serial servo adapter boards, power supplies, and 3D-printed parts (print them yourself or buy the kit).

📷 Cameras

One or two standard USB cameras (720p or 1080p), with a fixed mount: one at the front and another at the side or on the wrist.

🎙️ Voice

A basic USB or lapel microphone and a USB or 3.5 mm speaker.

🖥️ For training

A PC with an NVIDIA GPU, or Google Colab, to train policies in 5.4. Modules 5.1 and 5.2 run on a regular PC.

🧠 For running on the robot (optional)

Raspberry Pi 5 with 8 GB; with AI HAT+ 2 (about US$ 130) for small LLMs and VLMs; or Jetson Orin Nano Super (US$ 399 as of Jul/2026), which is more powerful and more expensive.

🛑 Safety

An on/off switch in series with the servo power supply, a clamp to secure the arm’s base to the table, and safety glasses.

✓ Worthwhile optional item

Access to a 3D printer (for replacement parts and camera mounts), a second camera, and a fixed workbench light.

✗ Don’t buy these for this trail

Hobby servo arm with PWM signal (SG90, MG996R): LeRobot cannot read their position. And don’t pay for a GPU without CUDA expecting to train policies.
